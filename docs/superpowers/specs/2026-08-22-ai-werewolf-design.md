# WFill AI 狼人杀整体设计

- 文档状态：待用户最终审核
- 设计日期：2026-08-22
- 首版范围：本地运行、6 人无警长、全 AI 自动对局、文本模型、真人观战
- 架构路线：模块化单体 + 事件驱动状态机

## 1. 项目目标

WFill 是一个以确定性狼人杀规则引擎为核心、以多个云端 AI API 为玩家控制器的文字狼人杀应用。首版让六个 AI 自动完成整局游戏，人类可以按公开、跟随角色或上帝视角观看。未来同一座位可以由任意已配置的文本模型或真人控制，并扩展至 9 人、12 人和更多角色版型。

项目的核心质量标准不是“多个模型能聊天”，而是：

- 角色只能获得依法可见的信息。
- AI 只能提交当前阶段允许的动作。
- 软件主持、计票、结算和判定胜负。
- 对局可以暂停、恢复、单步执行和确定性回放。
- 新角色和版型通过模块扩展，不在核心流程中堆角色名称分支。

## 2. 首版范围与非目标

### 2.1 首版包含

- 6 人无警长版型。
- 2 普通狼人、2 村民、1 预言家、1 女巫。
- 六个座位均由文本 AI 模型控制。
- 每个座位可以选择不同的已配置模型账户与模型。
- 自动播放、单步观战、暂停和恢复。
- 公开、跟随指定座位和上帝视角。
- 狼队夜间私聊、发言、投票、技能与胜负结算。
- 本地事件日志、对局历史、回放和 Token 统计。
- 简洁但固定的左右座位、中央信息舞台布局。

### 2.2 首版不包含

- 本地 AI 模型。
- 图像、语音或其他多模态输入。
- 真人作为玩家。
- 9 人、12 人和警长流程的运行实现。
- 狼美人、骑士、咒狐、丘比特等扩展角色的正式玩法。
- 公网房间、账户、匹配、排行榜、Steam 或云部署。
- 依赖 AI 的系统主持、计票或规则裁决。

这些能力保留架构接口，但不进入首版验收范围。

## 3. 已确定的产品原则

1. AI 是玩家，不是裁判或主持人。
2. 对局过程只称呼座位号，不称呼模型品牌。
3. 不请求、展示或保存模型思维链。
4. 系统播报由固定模板生成，不调用模型。
5. 真实状态在后端过滤后才能交给 AI 或前端。
6. 密钥不写入源码、Git、日志或回放；用户提供密钥，系统通过本地凭据存储管理。
7. 首版 UI 追求清楚和稳定，后续美化只修改装饰层。
8. 历史对局绑定不可变规则快照，后续规则升级不改变旧回放。

## 4. 首版规则基线

首版采用 `six-player-classic-no-sheriff@1.0.0`，完整细则见 `docs/rules/rulesets/6-player-no-sheriff.md`。

- 2 狼人、2 村民、预言家、女巫。
- 无警长、暗牌、屠城。
- 女巫一解药一毒药，不可自救，不可同夜双药。
- 首夜死亡与白天出局有遗言，后续夜间死亡无遗言。
- 首次平票进入 PK，再次平票无人出局。
- 所有选票收齐后统一公开，后调用的 AI 看不到先提交的票。

公开资料存在多个 6 人变体。本项目通过明确版型名称和版本固定上述规则，不声称它是唯一规则。常见的预女 6 人阵容可见[六人狼人游戏配置以及规则解读](https://www.langrensha.net/strategy/2021092802.html)；官方早期也提供过预言家、猎人的 6 人明牌无警长版本，并规定了首夜遗言和白天遗言，[规则介绍](https://langrensha.com/wanfa/guize/2017/10/18/26899_719311.html)；首次平票 PK、再次平票无人出局可见[狼人杀法官流程](https://www.langrensha.net/strategy/2021092601.html)。

## 5. 八个核心模块

### 5.1 对局内核

唯一有权改变真实对局状态，负责阶段推进、合法性校验、技能执行、死亡链和胜负判定。它不调用模型、不生成角色发言。

### 5.2 规则库

包含角色、技能、效果、版型、阶段和胜利条件。规则对象带稳定 ID 与版本，经过加载校验后形成每局不可变规则快照。

### 5.3 对局编排器

查询下一行动者，生成合法视图，请求玩家控制器，提交命令，持久化事件，并根据自动、单步或暂停模式继续推进。

### 5.4 玩家控制器

统一 AI、未来真人和测试脚本三种控制来源。角色身份与控制器解耦，换模型或换真人不会改变角色能力。

### 5.5 模型网关

统一不同文本 API 的鉴权、请求、结构化输出、流式文本、超时、取消、重试、Token 和错误分类。游戏层不依赖厂商字段。

### 5.6 信息投影器

从真实状态生成公开、指定座位、狼人阵营、上帝和系统私有视图。权限在后端过滤，前端不接收无权查看的数据。

### 5.7 事件存储

保存不可变对局事件、定期状态快照、模型调用元数据和回放索引。回放由事件重建，快照仅用于加速。

### 5.8 用户界面

提供模型配置、创建对局、中央观战舞台、视角切换、播放控制、结算和历史回放。

## 6. 依赖方向

- 规则库不依赖 UI、数据库或模型 API。
- 对局内核只依赖已加载的规则接口。
- 编排器依赖内核、控制器、投影器和事件存储。
- AI 控制器只通过模型网关调用外部 API。
- UI 只读取安全投影并提交应用命令。
- 提供商适配器不读取真实对局状态。

禁止规则模块直接写数据库、调用模型或向前端推送事件。

### 6.1 首版技术基线

- 语言：前后端与规则包统一使用 TypeScript。
- 运行时：Node.js 22 LTS。
- 工程结构：pnpm workspace 模块化单仓库。
- 前端：React + Vite，首版运行在本地浏览器。
- 后端：Fastify，提供 REST 命令接口和服务端事件流。
- 实时观战：首版使用 SSE 单向推送安全事件；未来真人实时双向通信再增加 WebSocket。
- 数据：SQLite，通过仓储接口访问，避免领域层依赖具体数据库。
- 运行时协议校验：Zod；AI 返回、命令、事件和配置都必须经过模式验证。
- 测试：Vitest 负责规则与模块测试，Playwright 负责浏览器端到端验收。
- 桌面封装：首版不引入 Electron 或 Tauri；未来 Steam 版本复用同一 Web UI 再评估封装。

选择单一 TypeScript 技术栈是为了共享命令、事件和视图协议，而不是让前端直接引用规则引擎内部状态。

## 7. 对局状态机

一级状态为：

```text
LOBBY → SETUP → NIGHT → DAWN → DAY → SETTLEMENT → FINISHED
```

- `LOBBY`：选择版型、座位、模型与运行参数。
- `SETUP`：校验配置、锁定规则、分配身份并创建私有视图。
- `NIGHT`：狼队交流、刀口、查验和用药等行动窗口。
- `DAWN`：统一应用保护、救治、伤害和死亡结果。
- `DAY`：系统播报、遗言、顺序发言、特殊行动和投票。
- `SETTLEMENT`：处理放逐、死亡触发、连锁效果和胜负。
- `FINISHED`：冻结状态、生成结算与回放。

行动窗口由版型配置，技能提交顺序不等于效果立即生效顺序。模型返回后必须检查对局版本和当前窗口，过期响应不得进入对局。

## 8. 命令、事件与结算

外部提交命令表达意图，例如发言、投票、查验、用药和狼刀。引擎校验后产生不可变事件。事件至少包含对局 ID、序号、规则版本、日数、阶段、类型、行动者、目标、可见性、原因事件和载荷。

死亡按以下顺序处理：

1. 收集死亡原因和待应用效果。
2. 应用保护、免疫、替代和阻断。
3. 确定最终出局玩家。
4. 开放合法死亡响应窗口。
5. 处理连锁死亡。
6. 运行胜负条件。
7. 生成按视角过滤的播报。

每个死亡保留明确原因，不能只保存 `alive=false`。

## 9. 角色与版型插件框架

规则包由五类对象组成：

- `RoleDefinition`：阵营、身份类型、技能引用和 AI 身份说明。
- `AbilityDefinition`：触发窗口、目标、资源、条件和效果。
- `EffectDefinition`：击杀、保护、查验、翻牌、禁票、关系和阵营变化等标准效果。
- `RulesetDefinition`：人数、阵容、阶段、投票、遗言和规则选项。
- `VictoryCondition`：获胜阵营、获胜玩家和结算优先级。

大多数角色通过标准效果声明式组合；真正改变结构的角色使用受控扩展执行器。执行器只能调用内核公开操作并产生事件，不能直接修改数据库。

标准生命周期钩子包括初始化、阶段开始与结束、命令校验、效果应用、即将死亡、确认死亡、投票结算、查验结果、视图投影和胜负检查。加载时验证钩子冲突与优先级。

未来扩展验证至少覆盖：插入行动窗口、建立玩家关系、修改查验或死亡结果、增加第三方胜利条件。

## 10. AI 提示词系统

每次提示词按固定层级组装：

1. 游戏最高约束。
2. 当前版型规则。
3. 当前座位的私有身份卡。
4. 可选人格与策略档案。
5. 当前座位依法可见的历史。
6. 当前唯一任务、合法动作和输出协议。

玩家发言位于明确的不可信内容区，不能覆盖系统规则。模型只获得座位号，不获得其他玩家的模型品牌。系统不要求模型展示分析过程，只接收公开发言或结构化行动。

发言与行动分离。自然语言中的“我要投 3 号”不产生规则效果，只有经过结构化校验的投票命令生效。

## 11. 发言预算与上下文

- 普通发言建议 80 至 180 个汉字，硬上限 220。
- PK、遗言硬上限 150。
- 狼队单次交流硬上限 100，每狼每夜最多两次。
- 技能附带台词硬上限 60。
- 未来警上发言硬上限 180。

先通过提示词和最大输出 Token 约束；超限时要求模型压缩一次，仍超限则在完整句子边界截断。

每个座位维护独立可见上下文。精确保留存活状态、公开身份、投票、技能资源、私有结果和近期原始发言；较早长文本可以压缩，但结构化事实不能交给模型自由总结。

## 12. 投票系统

投票是通用结构化模块，可配置候选范围、票权、权重、是否弃票、公开时机和多轮规则。

本轮投票开始时冻结所有投票者的公开输入视图。选票先作为私密待处理命令保存，收齐或超时后统一结算和公开，避免顺序调用 API 造成信息优势。系统负责计票、平票 PK、放逐和播报。

## 13. 系统主持

系统主持使用固定、可版本化和可本地化的模板。播报由事实事件投影产生，不调用 AI。公开视角只说依法公开的座位与结果，上帝视角可以附加死亡原因和技能链。

AI 的投降、阶段宣告、规则解释或胜利宣称均视为角色发言，不改变系统状态。

## 14. 界面结构

对局页面从首版固定为三栏：

- 左侧：一半玩家座位。
- 中央：阶段、系统播报、当前 AI 发言、历史记录、投票和结算。
- 右侧：另一半玩家座位。

顶部提供天数、昼夜、阶段、播放模式、速度、暂停和视角；底部提供单步、自动、暂停、视角与未来真人行动区。

座位卡只显示编号以及存活、当前发言、上警、警徽、投票、断线和依法可见身份等状态。首版 6 人左右各三席；9 人和 12 人保持对称并按顺时针编号。所有 AI 输出统一显示在中央，发言时仅高亮对应座位。

后续允许更换颜色、字体、头像、动画、音效和素材，不改变区域职责、命令接口和状态来源。不复制其他游戏的美术资产。

## 15. 观战视角

- 公开视角：只看公开发言、公开投票和系统公告。
- 跟随座位：看到该座位的身份、技能、私有结果和依法可见的队友信息。
- 上帝视角：看到所有身份、夜间行动和狼队私聊。

狼人私聊只对存活狼人和上帝视角开放。任何视角都不展示思维链、隐藏提示词或原始 API 响应。

## 16. 模型与密钥

模型账户配置由显示名称、提供商、端点、密钥引用、可用模型和健康状态组成。用户新增密钥后，系统增加对应账户配置；创建对局时只显示凭据存在且健康检查通过的文本模型。

真实密钥存入 Windows 凭据管理器或等价本地密钥库，不进入源码、Git、SQLite、日志、回放或提示词。用户不应在对话中发送完整密钥。未来云端只替换凭据后端，不改变模型配置接口。

## 17. 数据与回放

首版使用 SQLite 保存对局元数据、座位、不可变事件、状态快照、模型调用元数据和费用统计。真实凭据不进入 SQLite。

回放复用对局页面和信息投影器，支持公开、跟随和上帝三种级别。导出文件明确标记视角，不能把上帝回放误作无剧透回放。

每次模型调用记录座位、模型配置、用途、延迟、Token、重试、模板版本和错误分类；不记录密钥、请求头、内部推理或完整底层报文。

## 18. 失败与恢复

- 发言失败：有限重试后记为未发言。
- 投票失败：按版型执行弃票。
- 可选技能失败：默认放弃。
- 强制技能失败：暂停并允许更换模型或人工指定。
- 狼队未形成合法刀口：按版型进入确认或空刀。
- 服务重启：从最近快照和后续事件恢复。
- 重复命令：通过命令 ID 幂等处理。
- 过期模型响应：丢弃并记录，不改变状态。
- 达到硬 Token 预算：暂停，不擅自更换模型。

## 19. 安全边界

首版服务只监听 `127.0.0.1`。视角权限在后端执行，错误页面和普通日志不得显示请求头、凭据或完整敏感上下文。导出对局时只导出所选视角允许的信息。

公网真人模式需要单独设计账户、房间授权、WebSocket 鉴权、限流和服务端密钥管理，不能直接暴露本地服务。

## 20. 测试策略

### 20.1 规则单元测试

覆盖身份分配、刀杀、查验、药剂、不可自救、同夜双药限制、投票、平票、遗言、死亡原因和胜负。

### 20.2 状态机测试

验证每个合法转换、非法命令拒绝、暂停恢复、重复命令和过期响应。

### 20.3 信息隔离测试

为每个事件检查公开、每个座位、狼人和上帝投影，确保没有身份、刀口、查验或狼聊泄漏。

### 20.4 插件契约测试

使用测试角色验证新行动窗口、关系、结果修饰器和第三方胜利条件，无需修改核心引擎。

### 20.5 无 API 模拟对局

用确定性脚本控制器运行大量完整对局，验证规则和回放，不消耗 Token。

### 20.6 真实模型验收

接入用户配置的多个文本模型，检查格式服从、发言长度、角色目标、非法指令防护、费用和完整对局稳定性。

## 21. 首版验收标准

1. 六个 AI 可以使用至少两个不同模型配置完成一局 6 人游戏。
2. 规则引擎独立完成主持、投票、技能、死亡与胜负结算。
3. 三种观战视角的信息均正确，上帝之外看不到狼聊。
4. 普通发言不超过 220 个汉字，其他场景符合预算。
5. 所有选票统一公开，没有调用顺序信息优势。
6. 对局可以自动、单步、暂停、重启恢复并完整回放。
7. 无 API 模拟测试覆盖核心规则和至少四种扩展机制。
8. Git、SQLite、日志和回放中不存在真实 API Key。
9. UI 保持左右座位、中央信息舞台，6 人布局完整可用。
10. 历史对局使用原规则快照重放，规则升级不改变结果。

## 22. 后续扩展顺序

1. 首版 6 人 AI 自动局。
2. 真人座位控制器和本地人机混合。
3. 9 人版型与更多基础角色。
4. 12 人警长、四神四民四狼。
5. 狼美人、骑士、咒狐、丘比特等复杂插件。
6. 网络房间和云部署。
7. 语音输入输出、Codex Sites 或 Steam 评估。

每一步都必须通过规则、隔离、恢复和真实运行验收后再扩展。

## 23. 主要风险

- 不同狼人杀平台规则存在差异：通过版型版本明确规则，不追求不存在的唯一标准。
- 模型输出不稳定：结构化协议、校验、有限重试和默认行动。
- 上下文与费用膨胀：发言预算、独立可见记忆、摘要和硬预算暂停。
- 隐藏信息泄漏：后端投影、冻结输入和逐事件权限测试。
- 伪模块化：用扩展角色契约测试证明能力，而不是只留下接口名称。
- API 厂商变化：由模型网关隔离，模型和价格配置可更新。
